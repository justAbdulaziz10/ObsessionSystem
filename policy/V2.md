# AgentOS v2 — durable task lifecycle

Use this for substantial engineering work (multi-step, multi-file, delegated, or likely to outlive one session). Skip it for quick questions and small edits. Routing, model, and review rules live in GLOBAL.md and are not repeated here.

## Lifecycle

1. Start (or resume) durable state from the repo root:
   `agent-v2 start "<request>"` → prints the task id. Use `--new` to force a new task.
   Treat the task's spec, context, event log, plan, and proof as the source of truth instead of conversation memory.
2. Work. Delegate substantial implementation to the Codex HA layer (`agent-codex-worker`).
3. Prove: `agent-proof capture <task-id> --checks`. Also inspect the actual diff, tests, build, lint, and typecheck; capture visual before/after for UI work and comparable metrics for performance work. A worker saying "done" is not proof.
4. Finish, always, including on failure:
   `agent-v2 finish <task-id> --outcome success|partial|failure --checks`
   Unfinished tasks stay "running" forever and never become eval cases.
5. Switching account or session mid-task: `agent-handoff <task-id>`. The next account continues from durable state rather than restarting discovery.

## When something fails

If the same failure repeats twice: stop repeating the strategy, run `agent-recall "<error>"` (ranked pointers into recorded failures, lessons, decisions, SYSTEM.md and Claude memory; read only the entries it points to), then change strategy, tool, context, or worker and retry within a bounded budget.
When a recovery is proven: `agent-fail remember "<error>" "<resolution>"`.

## Boundaries

- `agent-guard "<command>"` is an advisory check before uncertain consequential commands. It is not enforced by a hook.
- External writes, secrets, production changes, and destructive operations need the appropriate confirmation.
- Give subagents the smallest tool surface they need. Coding workers do not need Gmail, Slack, production cloud access, or unrelated private connectors.
- codex-ha does not create worktrees: it runs in the current directory and locks it. Give parallel workers separate worktrees.

## Governance

- New Luna models are candidates (`agent-model-governor scan`). Promote only with real canary verdicts.
- After plugin updates, `agent-plugin-governor scan` detects changed hooks, MCP config, scripts, and executable plugin files. Installed plugin code is not blindly trusted after updates.
- `agent-research` inspects orchestration performance from finished tasks to form experiments.
- Prefer ablation and deletion of dead-weight harness layers over accumulation. The best harness is the smallest one that repeatedly produces the strongest verified result.
